这些实验还暴露语义风险：Gnome **初次草案**把原网格名含 `wormie` 的物件称为“企鹅”。程序会列出这种命名不一致，但不能据此自动确认物体类别；需要看图审核。最终全新试验的三档没有这类命名警告，但仍需人工检查原物件计数和摆放自然性。`candidate` 不意味着 gold answer 或 30 次操作难度已验证。

模拟上游服务测试覆盖了 Claude Code CLI → 本地协议桥 → OpenAI Chat Completions → 流式 Anthropic 响应，含图片、工具调用、65,536 输出 token 上限、缓存统计和 429 后重试。真实试跑期间没有发生 429，因此真实 429 的等待时长尚未实测。

## 1.2 协议的构建验收

`examples/ten_by_three_garden_plan.json` 是手工编写的 10 类题型协议样例，沿用 garden 场景原始 GLB。它没有经过 DeepSeek 自动规划；用途是验证新版结构、三次独立导出和判定逻辑。实际 Blender 构建与 `sceneqa verify` 均完成：简单题 `count` 答案 5，困难题 `identity` 答案为 `teacup_and_saucer`，程序均可从注册表与地标关系核对；中等题 `color` 的“蓝色”由样例计划声明，程序无法核实颜色语义。三档可见性检查均通过，困难题的最近地标距离分别约为 6.94 和 13.23（世界 XY 单位）。因此总状态是 `needs_review`，不是正式 gold。新版 10 类随机选择是否能由 DeepSeek 稳定完成，仍需单独实测。

随后使用同一真实 garden GLB 对 `1.2` 协议做了一次**全新 DeepSeek 自主规划试跑**，不复用手写计划。模型按随机题型表选择了 `count`、`pattern`、`pose`，在同一 Claude Code 会话中先因一个不存在的原始 mesh 名失败，随后修正计划、导出三档 GLB，并通过全部结构和可见性检查。三题分别为草坪硬币数量（模型计划未声明答案，旧版程序算出 5）、蘑菇伞盖图案（模型答“红色伞盖上布满白色圆点”）、最近蘑菇下纸夹的姿态（模型答“平躺在草地上”）。整体状态为 `needs_review`，因为后两题答案未自动核对。该次会话使用 34 次成功 API 调用、1 次未完成尝试，输入 778,088 tokens，其中 727,168 命中缓存，命中率 93.46%；无 429 重试。此结果验证了生成流程，但也显示模型会花时间查看命令帮助和修复 mesh 名称。

用户随后明确要求**不自动核验答案，由模型看图自行作答**。因此 `1.3` 协议将上述 `1.2` 的混合答案方式改为：十类题均填写 `declared_answer`，输出 `reveal.png` 与 `detail.png`，模型必须打开六张图片；程序仅验证导出、遮挡和地标关系，不核对答案。手写 `1.3` 样例已完成三档构建与 `candidate` 校验，三个答案均标记 `model_visual`、`answer_verified: false`。这只证明管线语义和图像输出工作，不证明模型答案正确。

**DeepSeek 图像作答试验。** 将手写 `1.3` garden 样例的每档 `start/reveal/detail.png` 三张图发给同一个 `deepseek/deepseek-flash` 模型，让其只看图短答，三次 API 请求均返回 HTTP 200：硬币总数答“2枚”（样例计划登记 5），蘑菇桌下纸夹答“蓝色”（与样例一致），最近蘑菇下物体答“一个杯子”（与样例的“茶杯和茶碟”部分吻合）。这说明直接让模型看三图能回答局部颜色，但无法保证分散物体的计数；生产提示词因此要求计数题所有相关物件在证据图中可清点，不能确认时换题或调整摆放。该试验不把样例登记答案当作自动核验器，也不修改模型的原回答。

**`1.3` 端到端限制。** 两次真实 garden 全流程重跑均在计划写出前因模型长时间探索或上游多图请求延迟被主动中止，不能记作 `1.3` 的端到端成功。第一次 22 次 API 尝试后仍在解包内嵌纹理；第二次加入“不要解包纹理”提示后停止了该行为，但一次多图请求持续数分钟。代码层的三档构建/校验和独立 DeepSeek 看图作答已分别验证，完整一次会话自动交付仍需后续成功试跑。
