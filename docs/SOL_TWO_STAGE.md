# Sol 批量流程：先筛场景，再增强出题

> 此文包含早期 K8s / Sol 运行记录。当前默认已改为本地渲染，模型/provider可替换；现行配置以 [README](../README.md)、[模型接口](MODEL_INTERFACE.md)、[渲染后端](RENDERING.md)为准。历史批次保留原协议。

两步独立运行。第一步只决定原始素材留或删；第二步才修改场景、设计题目和让模型看图作答。场景筛选不再要求素材现成支持三道题。

逐件看图和判断由 `gpt-6.1-sol` 批量完成，不需要逐件人工核对才能继续。程序负责下载、远程渲染、请求重试、缓存、进度和清单；小量抽查用于修改 prompt，不作为每件必经步骤。

## 1. 场景筛选

完整入口接受 JSONL，每行 `uid` 加一个 `url`，或本地 `source_glb`。它先下载并检查 GLB，再在 K8s 生成八视角，最后让 `gpt-6.1-sol` 判断是否有连贯布局、多种可辨物件和转动/放大观察的收益。模型只交付 `uid`、`decision`（`keep` 或 `reject`）、`reason`。

程序保存逐件结果、原始响应、输入哈希与 token usage。缺图或请求失败单独记录为运行失败，不能当作素材删除；重跑使用缓存。筛选记录不移动或删除原件。

```bash
export LUNA_API_KEY=...
python3 tools/scene_pipeline.py \
  --sources sources.jsonl --out /data/screen \
  --pod scene-sol-screen-batch --workers 3
```

有已有远程图片时，加 `--captures /data/captures`，直接复用 `captures/UID/az_045_overview.png` 等图片。`--max-bytes` 默认 35 MiB；`--url`、`--model`、`--key-file` 可配置接口。单纯读取图片筛选的底层入口仍是 `tools/scene_screen_batch.py`。

输入示例：`{"uid":"room_001","url":"https://example.org/room.glb"}`。输出 `keep.jsonl` 和 `reject.jsonl`；下载或渲染失败另记，不误记为删除。源地址、许可证等输入字段会保留在清单里。

## 2. 场景增强与三档出题

输入是筛选后原始 GLB 路径。先在 K8s 检查场景和少量原生物件组，再让模型设计三次独立增强。只复用原场景物件，三题选不同物件类别和题型，不能只改同一题的数量。题型沿用仓库的十类：数量、身份、颜色、图案文字、姿态状态、包含承载、相对位置、远近排序、尺寸比较、部件连接。

模型用 `ids` 选择完整物件组，用 `support` 与 `at: [u, v]` 指定支撑面及面内位置，不必计算原物件到目标位置的坐标差。程序按实际表面贴合物件，再渲染成品。每轮只用一次规划调用和一次三档联合看图回答调用，默认失败再改一次。

- 简单：初始角度看不到关键答案，改变视角后能找到。
- 中等：需要绕开自然的局部遮挡物观察。
- 困难：先按唯一线索在至少两个相似候选目标或区域中选定一个，再去找被挡住的内容。删去第一步后，若剩余描述仍唯一指向目标，就不满足必要两跳。

难度描述的是观察过程，不强求操作轮数。合并网格、找不到完整可复用物件、无法自然出题的素材可记为 `unsuitable`，不强行构建。

```bash
python3 experiments/sol_augment/run.py \
  --queue /data/screen/keep.jsonl --out /data/augment20
```

每个可用场景交付简单、中等、困难三套 `scene.glb` 和 `question.json`，附初始相机及起始、揭示图片。答案由模型查看实际成品填写；程序只负责文件和运行状态，不计数或推导答案。模型自评通过不等于独立正确性认证。

## 3. 出题与审核闭环

当前批量闭环入口把生成、独立看图审核和返修连在一起，不需要手工把失败原因复制给生成模型：

```bash
python3 tools/scene_feedback_loop.py \
  --sources /data/screen/keep.jsonl --out /data/loop --max-repairs 2
```

使用同一套原生物件增强接口；当前闭环从原景只生成一道中等题，避免其他档位的构建失败阻断中等题。也可从已有三档结果继续修中等题。题目必须是观察者探索后能回答的问题，不能是复制或建模指令、不能题干直接给出所问答案；候选答案必须回应问题。定位线索不能用目标或同款物件的名称提示待答属性，例如问袋上印的物品名时，不能用“面粉袋”定位；计数题仍可正常写物件类别。这些由模型看图审核，程序不判断语义答案。每次审核只提交这道题、模型答案和实际场景的起始、揭示、区域及总览图片，不发送生成器的自评理由。审核失败时，模型在短 JSON 中给出具体原因和 `repair_action`，程序按其选择执行：

- `question`：只修指代、措辞或候选答案，保留场景与相机。
- `view`：从已有真实相机中重新选择起始与揭示视角，同步初始相机。
- `scene`：用原始 GLB 的完整原生物件重建中等档，在 K8s 渲染后重新看图作答。

修改后必须再进行独立审核。通过即保留；默认首次审核加最多两次返修，仍失败则剔除。首次生成若规划或落地构建失败，可以回传具体技术错误再试一次；首个有效成品直接交独立审核，不以生成器自评决定反复重建。未改变题目、答案或视觉证据的返修直接结束，不对原样题目反复评分。API 或文件处理失败标为 `failed`，不能算质量剔除。已有失败输出可续跑，旧版本、原始响应与调用缓存保留；只修文字或已有视角不会启动 GPU。没有程序化答案判真。

审核共享缓存保存相同题目、答案、GLB、图片和审核协议的首次有效结论，PASS 与 FAIL 都保存，跨运行目录复用，防止接口重试或代码修复后重复询问原题“刷通过”。真正改变题目、视觉证据或审核协议后才重新审核。`--review-cache` 可配置共享目录；默认使用输出目录中的 `review_cache`。所有后来的相反意见仍保留在历史记录中，缓存只是冻结该协议的第一次测量，不证明裁判正确。

`keep.jsonl`、`reject.jsonl`、`failed.jsonl` 和 `gallery.html` 在输出根目录。通过题目的 `folder` 指向 `delivery/{scene.glb,question.json,start.png,reveal.png,audit.json}`，保存题目、答案和初始相机。图册直接展示每轮题目、答案、起始/揭示图和审核意见。三档审核意见与中等单题审核意见各自记录，不能互相当作通过证明。

若要从已有增强继续修题，在输入行添加 `result`，不用重新做初次增强：

```json
{"uid":"room_001","source_glb":"/data/original.glb","result":"/data/augment/room_001/result.json"}
```

原始场景可使用 `source_glb` 或 `url`。每次运行保存源码快照和源文件/题图指纹；当前运行由 `UID/current_loop.json` 指定，新任务失败不能回退旧任务的成功交付。默认每批复用一个专用远程 worker，完成后释放；`--keep-pod` 可保留给后续运行。模型的通过状态仍是模型意见，不是人工真值。

闭环状态回归检查不调用接口、不处理或渲染 3D，也不核验语义答案。覆盖返修后再审、返修耗尽、审核请求失败、无改变返修、完成缓存，以及新运行失败不能恢复旧版保留结果：

```bash
python3 -m unittest discover -s tests -p test_scene_feedback_loop.py -v
```

单独使用原三档实验入口时，可另行导出该实验的完整套组；闭环入口已经自动整理通过的中等题：

```bash
python3 tools/export_scene_delivery.py \
  --work /data/augment20 --out /data/delivery \
  --sources /data/screen/keep.jsonl
```

交付目录为 `delivery/场景ID/simple|medium|hard/{scene.glb,question.json,start.png,reveal.png}`，另有逐题清单和原素材来源清单。导出前检查三个 GLB 和截图确实存在；正在返修的场景不会导出。同一 UID 的最新运行由 `current_run.json` 指定，当前失败时不回退旧版成功。默认保留完整套组的模型自评状态，若只要自评通过套组可加 `--only-model-pass`。修题后尚未自评的状态保留为 `null`；已有独立模型审阅记录会另附，不冒充人工 gold。

## 可选：模型复审与仅修题目

下面是手动调试原三档实验的审阅入口；上面的闭环已经自动执行中等单题审阅。另一个独立上下文中的 Sol 看成品、题目与候选答案，检查是否都有视觉证据和实际观察难度，不按代码计算答案。`uids.txt` 每行一个场景 ID。

```bash
python3 tools/independent_qa_audit.py \
  --baseline /data/augment --queue uids.txt --output /data/audit \
  --regions --overviews --require-terminal
```

当前按用户要求优先确认中等题是否可用，不再因困难题失败连带剔除中等题。单独检查中等题时，使用：

```bash
python3 tools/independent_qa_audit.py \
  --level medium --baseline /data/augment --queue uids.txt \
  --output /data/medium-audit --regions --workers 4
```

该模式只判断这一道题：指代与位置参照清晰、起始答案受真实局部遮挡、换视角后证据足以支持答案、物件摆放自然。画面太远或目标太小不能单独证明遮挡；不要求两跳，也不检查三道题是否使用同类物件。只发送该档实际图片与题目答案，缓存与统计独立于三档审核。`pass` 是模型对中等单题的意见，不代表整套三题通过。

若问题仅是指代或措辞歧义，可修文字而保留已有 GLB 和相机，避免重建又引入摆放错误：

```bash
python3 experiments/sol_augment/revise_question.py \
  --result /data/augment/UID/result.json \
  --critic /data/audit/UID/record.json --out /data/revisions/UID
```

程序只允许修改模型审核指出的档位，其他题目保持原样。修订不继承旧题的自评通过；需对新的完整三题再审一次。此入口不自动无限返修，物理遮挡或必要两跳不成立时，不能靠重写措辞宣称解决。

详细参数与限制见 [增强脚本说明](../experiments/sol_augment/README.md)。这条简化流程与旧版 `sceneqa run` 的六候选探测流程各自独立，批量实测记录会标明使用哪条流程。

## 2026-09-30 实测

筛选阶段通过 103 relay 实际调用 `gpt-6.1-sol`。同一组 20 件的三版提示结果分别为 14 留 / 6 删、16 留 / 4 删、13 留 / 7 删。最终版增加“素色不等于坏资产”和“建筑结构、重复装饰不算丰富物件”两项短规则，避免把静态图上的灰墙误删，也避免凭墙面和彩色构件凑数。

最终版 20 件均成功返回；另对 7 件以前核对过的场景使用同一版筛选，7 件均保留。两组分母分别统计，合并得到 20 个去重原始 GLB 作为增强测试输入。这些留删是模型对素材的判断，不是问答正确率。研究记录位于工作区 `research/native-qa-source-search/goal_1000/sol_scene_screen/`。

另从既有 K8s 八视角素材固定选择 50 件此前未经过 Sol 筛选的场景，使用仓库入口、同一短版 v3 prompt 和 4 并发完成自动筛选：**27 留、23 删、0 失败，耗时 270.70 秒**。50 件响应模型均为 `gpt-6.1-sol`。4 次 HTTP 502 各重试一次后成功；新请求用量 307,948 tokens，供应商报告缓存 5,760 prompt tokens，首次本地缓存命中 0。另复跑 3 件缓存一致性检查，全部命中、结果一致，新增 token 为 0。没有逐件人工看图或补判。固定队列、完整来源、留删清单、进度、原始响应和中文图册位于工作区 `scene-qa-runs/sol-scene-screen-extra50-v3/`。

增强基线 20 件已在两台独立远程 worker 完整跑完：**10 件模型自评通过、3 件自评未通过、3 件不适合增强、4 件处理失败**，耗时约 56 分钟，80 个实际 API 响应用量合计 798,791 tokens。13 件最终有三份有效 GLB 和模型答案，共 39 道题；另有一件曾构建三 GLB 后处理失败，不能作为完整交付。模型自评通过数不是答案真实正确率。完整中文图册在工作区 `scene-qa-runs/sol-augment20-v3/gallery.html`，扁平交付与失败清单在 `scene-qa-runs/sol-augment20-v3-delivery/`。

处理失败包括旧版空 AssertionError、非三角 Path3D 兼容问题及两件远程内存不足。当前版已使用明确字段错误、仅将三角网格送入渲染器、共享原几何与材质，避免复制全场景纹理造成内存峰值。筛选只渲染八张源景图，不提前制作增强所需的物件联系图；完整 URL 链路已用当前渲染方式重新测通并验证复跑缓存命中、新增 token 为 0。

完整 URL 下载 → K8s 八视角 → Sol 筛选 → `keep.jsonl` 链路另用一件真实资产测通。缺文件、缺图的批次验证各自记录失败；两件有效素材同输入复跑缓存命中，新增 token 为 0。导出工具已对基线 13 件完整成品的 39 套扁平交付检查文件，并验证最新版本、运行中、失败和越界目录四种版次处理。

对五个已完成、包含早期风险案例的场景另开独立 Sol 图像审阅，5 件均未通过：同类栏杆或地灯重复改问、简单题初始即可答、悬浮摆放、答案关键形状无法确认。这不是随机总体正确率，也不是人工 gold；它证明当前生成器的自评通过不能作为入库依据。

后续对四件同素材做支撑面坐标修订测试：1 件自评通过、2 件当前物件接口不适合、1 件支撑落点处理失败。农舍曾得到独立模型 PASS，但三题实际全为计数，困难题第一跳可绕过；该次审核漏查了要求，历史 PASS 保留并标明覆盖不足，不能算合格样本。

补回题型多样性与必要两跳的短规则后，又实测酒馆和农舍两件：酒馆交付三份 GLB，但独立审阅认为简单题指代不唯一；农舍两轮都选到无实际表面的支撑区域，记为处理失败。支撑表面未命中时程序提供附近实际命中的位置建议，仍不伪造落地位置，也不按复制数量生成答案。

最后只让 Sol 修酒馆简单题，保持三 GLB、机位及中难题文字不变。一次新独立审阅对简单、中等题给出支持证据，但整套仍 FAIL：困难题删除“先找到壁炉”后，后续地址仍能唯一定位，第一跳冗余。修题加审核共 24,408 tokens；记录位于工作区 `scene-qa-runs/sol-augment-v5-question-revision-audit/`。没有重复抽样直到得到 PASS，也没有据此推算总体合格率。

本轮完成的是批量筛选入口、20 场景增强测试及上述优化。筛选可以按清单运行；三档生成目前仍是实验入口，尚未证明能稳定产出全部符合难度要求的题组。

### 放宽困难题要求后的中等单题检查

按用户要求单独检查中等题，复用已有实际截图，未重新渲染、改题或改答案。固定基线 13 道完整中等题，本轮 Sol 判断 9 道通过、4 道剔除（69.2%）；另外单列农舍与酒馆两个优化版本，1 道通过、1 道剔除。共 15 个题目版本、13 个原始场景，无处理失败。4 并发实际耗时 153.72 秒，新用量 32,873 tokens，全部响应模型为 `gpt-6.1-sol`。

剔除原因包含指代不唯一、只有放大而无真实遮挡、揭示图证据不足，以及图中有围栏但候选答案说没有。另有新旧模型审阅意见冲突，且部分证据集不同；本轮比例只能解释为本次模型单题审核通过比例，不能视为真实正确率或稳定入库率。原始全套 FAIL 不再自动否定中等题；原始意见与本轮意见都保留，不挑选较好的结果覆盖历史。

中文逐题图册、固定来源、留删清单及冲突说明位于工作区 `scene-qa-runs/sol-medium-only-audit-20260930/`。后续可按档位保留质量意见，不必要求困难题通过才能留存中等题。

### 出题、审核与返修的闭环实测

固定使用酒馆、灯塔、农舍三个原始场景，实际响应模型为 `gpt-6.1-sol`。两个已有成品从审核继续，农舍从原始 GLB 生成：首次支撑面未命中，具体技术错误回传后，第二个计划在 K8s 构建出有效中等场景。每个有效版本都再交独立上下文看实际图片审核；模型自评不是保留门槛。

| 场景 | 实测失败与返修 | 当前模型意见 |
| --- | --- | --- |
| 酒馆 | “被遮挡桌面”指代不唯一；模型补充壁炉、墙和木桶线索，重新看图回答蜡烛状态，再审 | PASS |
| 灯塔 | 起始图已看到围栏；改问窗户后仍直接可见；第二次修题改为被屋顶遮挡的另一面墙 | PASS |
