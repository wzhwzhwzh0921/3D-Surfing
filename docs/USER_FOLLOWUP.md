# 基于原题的用户追加增难

`followup` 是二次处理入口，输入一批已经审核通过的原题。原始场景、原题文字和初始相机保持一致，模型扮演用户提出新的要求。追加需求不会包含原题答案，也不会伪造助手已经回答的对话。

两种模式：

- `bundle`：保留原题，再追加两个不同目标的问题。合计至少两种题型、两个内容不同的区域，初始图不能直接回答任何一项，且需要有不同信息的证据视角。交付时三个要求都必须回答，任意一项错误则整题不通过。
- `chain`：以原题找到的目标为起点，连续完成两次空间选择，再观察最后目标的隐藏属性。每次选择需有至少两个真实候选，后一步依赖前一步。独立审核会检查删除某一跳后，下游描述是否仍能唯一定位；能删掉的步骤不能计入有效推理链。

两跳空间关系可能在同一张探索后的图中清楚呈现，这仍可增加推理要求。链条模式不强制增加证据视角数；跨多个有不同信息的证据视角是多目标模式的要求。两者都保留原题的初始遮挡条件，不把更多截图或更多操作次数直接当作推理难度。

```bash
python3 -m scene_factory workflow followup \
  --campaign /path/to/completed-campaign \
  --out /path/to/followup-run \
  --modes bundle chain --limit 4 \
  --max-repairs 1 --inspection-rounds 2
```

输入读取 `selected.jsonl` 对应的原始 GLB、原题交付和已有取景。会核对原景截图及局部图的文件哈希，再通过配置的模型后端调用。默认 Codex + ChatGPT 登录，模型与 provider 可替换，见[模型接口](MODEL_INTERFACE.md)。`--uids` 可以明确指定本次对照的场景，`--modes` 可以只测试一种方案。

本轮多图推理实际出现过超过240秒的调用，`followup` 默认将单次 Codex 等待预算设为480秒，给600秒的HTTP等待保留清理余量。显式 `SCENEQA_CODEX_TIMEOUT` 仍优先。429/5xx等现有重试继续执行；其他工作流的默认超时不变。

模型可以请求 bbox 换焦、旋转和缩放补充证据，每轮最多两张，参数由模型填写。新增渲染默认在本地子进程执行，设置 `SCENEQA_RENDER_BACKEND=k8s` 后使用集群，见[渲染配置](RENDERING.md)。不会为了这次文字增难复制或修改场景物件。

相机绕焦点运动时，正pitch抬高相机，负pitch降低相机。俯瞰地面应抬高相机；这与“把镜头向下转”不是同一参数。换焦射线命中屋顶时焦点就在屋顶，不能假设穿透到了地面。

每个模式按“用户需求规划 → 实际图片作答 → 独立上下文审核 → 只返修追加需求”处理。程序校验字段、原题一致性、依赖关系、证据引用和审核项完整性；所有事实答案、遮挡结论及推理有效性由模型观察判断，不从几何或复制数量自动核验。

输出：

- `keep.jsonl` / `reject.jsonl` / `failed.jsonl`：明确保留、质量剔除、处理失败；不删除原资产。
- `<uid>/<mode>/delivery/scene.glb`：原始场景文件，保留原材质数据。
- `task.json`：两条 user 消息、原题、追加需求、逐项作答要求、原始相机及全对规则。该文件不含答案或内部推理候选。
- `answers.json` / `audit.json`：评估侧的模型答案与独立审核；不要交给解题模型。
- `record.json`、逐轮原始响应和 `gallery.html`：本轮质量、返修及图片证据。

同一个输出目录绑定原题、相机、素材哈希、模型接入指纹、prompt、渲染代码和实现哈希。协议变化需使用新输出目录，不能沿用旧审核结论。

这些是模型审核结果，不是人工 gold。当前没有用盲解 agent 测量真实探索次数；增加子问题主要增加完成任务的工作量，空间推理链是否有效需要逐例检查，不能把文字长或步骤数直接当作难度。
